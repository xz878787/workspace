# 《天龙八部》RAG 系统详解：从 EPUB 到智能问答

---

## 金字塔·顶层结论

**一句话说清楚本文在讲什么：**

> 我们用 Node.js + LangChain + Milvus + 通义千问，搭建了一个完整的 RAG（检索增强生成）系统。把《天龙八部》这本 EPUB 电子书"喂"给 AI，让你可以用自然语言向它提问——"段誉会什么武功？""乔峰的身世是什么？"——AI 能从小说原文中检索出相关段落，再基于这些段落生成准确、有据可查的回答。

**把它想象成：** 你请了一位读过《天龙八部》一万遍的"书童"，他不仅能把全书内容倒背如流，还能在你问任何问题时，立刻翻到相关段落，用自己的话解释给你听。这位"书童"就是我们用代码搭建的 RAG 系统。

**为什么这件事值得做？**

大语言模型（LLM）有两大痛点：一是"知识截止日期"（训练数据停在某个时间点），二是"幻觉问题"（遇到不知道的会编造答案）。RAG 的核心思想就是：**不要只靠模型的记忆，让它去查资料再回答。** 就像开卷考试 vs 闭卷考试——给模型一本书，它答得远比凭记忆靠谱。

## 金字塔·系统全景（四层架构）

在深入代码之前，先建立全局认知。整个系统分为两个管道、四个层次：

```
                      ┌──────────────────────────────────┐
                      │        《天龙八部》RAG 系统        │
                      └──────────────────────────────────┘
                                    │
            ┌───────────────────────┴───────────────────────┐
            │                                               │
    ┌───────┴────────┐                            ┌────────┴───────┐
    │  摄入管道       │                            │  查询管道       │
    │  (main.mjs)    │                            │  (rag.mjs)     │
    │  书 → 向量知识库│                            │  问题 → 答案    │
    └───────┬────────┘                            └────────┬───────┘
            │                                               │
    ┌───────┴────────┐                            ┌────────┴───────┐
    │ ① 加载 EPUB    │                            │ ① 理解问题      │
```

**两个管道的关系：** 摄入管道是"建图书馆"（一次性工作），查询管道是"去图书馆查资料"（每次问答都要做）。没有前者，后者就无书可查。就像你不可能在空书架之间"找到"任何一本书。

# 上篇：摄入管道（main.mjs）

## 先讲结论：摄入管道到底干了什么？

**从外面看，它只做了一件事：**

> 把 `天龙八部.epub`（一个 15MB 的电子书文件）变成 Milvus 向量数据库里几千条"语义索引卡片"。

**从里面看，它做了四件事（每件事对应一层）：**

| 层次 | 做什么 | 输入 | 输出 |
|------|--------|------|------|
| 文档加载 | 解析 EPUB 文件，按章节拆成 Document | `天龙八部.epub` (15MB ZIP) | 几十个 Document（每个对应一章） |
| 文本分块 | 把每章的长文本切成小片段 | 一个章节（几千字） | 十几个 chunk（每个 ≤500 字符） |
| 向量化 | 调用 Embedding API，把文本变成数字 | 一段文字 | 1024 个浮点数（语义向量） |
| 索引入库 | 把向量+原文一起存入 Milvus | 向量 + 原文 | 数据库中的一条记录 |

**核心比喻——"涮肉加工厂"：**

把一本小说变成一个可语义搜索的知识库，就像把一整头牛加工成火锅店里的涮肉片：

> - **EPUB 加载** = 把牛从冷库搬出来（从 ZIP 中解压出内容）
> - **文本分块** = 切成薄厚均匀的肉片（chunk_size=500，每片刚好一口）
> - **向量化** = 给每片肉贴上"风味标签"（1024 维语义指纹）
> - **入库** = 整齐码进冷藏柜，建好索引方便快速取用（IVF_FLAT + COSINE）

## 第一层：EPUB 加载——把电子书"拆开包装"

### 先讲结论

```javascript
const loader = new EPubLoader(EPUB_FILE, {
  splitChapters: true
});
const documents = await loader.load();
// → 得到几十个 Document 对象，每个对应书中的一章
```

**这两行代码做了什么？** 把一个 `.epub` 文件变成了结构化的 Document 数组，每个 Document 包含一章的纯文本。

### EPUB 到底是什么？

这是理解本层的关键。很多人以为 EPUB 是一种"格式"，更准确地说，**EPUB 是一个 ZIP 压缩包**。如果你把 `天龙八部.epub` 的后缀改成 `.zip` 再解压，会看到这样的目录结构：

```
天龙八部.epub (解压后)
├── mimetype                      # 声明：我是 EPUB 文件
├── META-INF/
│   └── container.xml            # 容器描述：内容在哪
└── OEBPS/
    ├── content.opf              # 元数据：书名、作者、章节列表
    ├── chapter1.xhtml           # 第1章 · 青衫磊落险峰行
    ├── chapter2.xhtml           # 第2章 · 玉壁月华明
    ├── chapter3.xhtml           # 第3章 ...
    └── ...                      # 更多章节
```

**关键洞察：** EPUB 里面每章是一个独立的 HTML/XHTML 文件。这意味着"按章分割"是 EPUB 天然支持的操作——不是靠正则匹配"第X章"来猜边界，而是直接按文件边界来切。这是 EPUB 相比于 TXT/PDF 做 RAG 的先天优势。

### EPubLoader 做了什么？

EPubLoader 在底层默默完成了四步操作：

1. **解压 ZIP** —— 把 `.epub` 在内存中解压
2. **解析 XML** —— 读取 `container.xml` 和 `content.opf`，找到所有章节文件
3. **提取 XHTML** —— 读取每个章节的 HTML 文件
4. **清洗标签** —— 把 `<p>`、`<div>`、`<span>` 等 HTML 标签剥离，只保留纯文本

**`splitChapters: true` 是点睛之笔。** 如果设为 `false`，整本书会被揉成一个巨大的 Document——就像把一本 50 章的书的每一页撕下来，重新装订成一个卷轴。检索时你无法知道"这段内容出自第几章"——这个元信息的丢失在问答场景中是致命的。用户问"虚竹什么时候出场"，你不仅要找到相关内容，还要能告诉他"这是第 36 章"。

### 为什么不是每个 EPUB 都能直接用？

EPUB 规范虽然统一，但每家出版社的实现质量天差地别。有些 EPUB 中夹杂着插图页、版权声明页、出版信息页。这些"噪音章节"内容极短（不到 100 字符），没有语义价值。代码中用了一段过滤逻辑：

```javascript
if (chapterContent.length < 100) {
  console.log(`跳过第 ${chapterIndex + 1} 章（内容过短，可能是插图页）`);
  continue;
}
```

这是在"清洗数据"——永远不要信任原始数据的质量。垃圾进，垃圾出。

## 第二层：文本分块——"切涮肉"的艺术

### 先讲结论

```javascript
const textSplitter = new RecursiveCharacterTextSplitter({
  chunkSize: 500,     // 每片最多 500 字符
  chunkOverlap: 50,   // 相邻两片重叠 50 字符
});
const chunks = await textSplitter.splitText(chapterContent);
```

**文本分块解决的核心矛盾：** Embedding 模型一次只能处理有限长度的文本（text-embedding-v3 最大 8192 个 token，约 6000 个汉字），而一个小说章节可能有几千甚至上万字。你必须把一章"切碎"才能喂给模型。但怎么切？切在哪里？切多大？这三个问题的答案，决定了你的检索质量。

### 为什么是 500 字符？（chunkSize 的选择哲学）

这是整个系统中最重要的"调参"决策。用表格对比各种选择的利弊：

| chunkSize | 优势 | 劣势 | 适用场景 |
|-----------|------|------|----------|
| 100 字符 | 检索精确，定位到具体句子 | 上下文太少，向量语义弱 | 短问答、FAQ |
| **500 字符** | **语义完整 + 粒度适中** | — | **小说/长文 RAG** |
| 2000 字符 | 上下文丰富 | 检索时语义被稀释，噪声多 | 文档摘要 |
| 5000 字符 | 接近一章 | 一篇里混杂多个主题，检索不准 | 整章分析 |

**比喻：** 500 字符 ≈ 金庸小说中一段完整的情节叙述。比如："段誉在无量山剑湖宫底遇到了神仙姐姐的玉像，磕了一千个头，得到了凌波微步和北冥神功的秘籍。"——这就是一个完整的"语义单元"。你不会想把它从中切开，因为前后两句是因果关系的整体。

如果 chunk 太大（2000 字符），就像一个装了三道菜的盘子——用户问"鱼香肉丝什么味道"，你端上来一盘装着鱼香肉丝、宫保鸡丁、麻婆豆腐的拼盘，模型要从三种菜里分辨哪个是鱼香肉丝，容易搞混。如果 chunk 太小（100 字符），就像把一盘菜分装成十碟，每碟只有一口——吃到嘴里味道是对的，但你不知道这道菜的全貌。

### 为什么要有重叠？（chunkOverlap 的智慧）

```javascript
chunkOverlap: 50  // 相邻两个 chunk 之间有 50 个字符是重复的
```

**这是初学 RAG 最容易忽略但最关键的一个参数。**

假设没有重叠（chunkOverlap=0），文本被这样切割：

```
chunk1: "...虚竹在少林寺中默默无闻地做了二十三年和尚。这一日，他随师"
chunk2: "父下山化缘，途中遇到了一位老妇..."
```

注意！"师傅"这个词刚好被切在边界上——"师"在 chunk1，"父"在 chunk2。检索"虚竹的师傅是谁"时，chunk1 里只有"师"没有"父"，chunk2 里的"父"也脱离了上下文。**信息在边界处丢失了。**

有重叠（chunkOverlap=50）后：

```
chunk1: "...虚竹在少林寺中默默无闻地做了二十三年和尚。这一日，他随师父下山化缘"
chunk2: "...做了二十三年和尚。这一日，他随师父下山化缘，途中遇到了一位老妇..."
```

重叠部分像"粘合剂"，确保边界处的信息不会因为切割而丢失。

**比喻：** 就像你用两张壁纸贴一面墙——两张纸之间必须有 1-2 厘米的重叠，否则接缝处会漏出墙面的底色。chunkOverlap 就是 RAG 世界里"壁纸的重叠区"。

### "递归"字符分割器的递归策略

RecursiveCharacterTextSplitter 的名字里带着"递归"，它到底怎么个递归法？

它有一个内置的"优先级分隔符"列表（默认值）：

```
["\n\n", "\n", " ", ""]
```

分割时按以下策略逐层尝试：

1. **第一优先级 `\n\n`（段落分隔）** ——在整个文本上先按段落边界切。绝大部分情况下，段落是最自然的语义边界。
2. **如果某段仍然 > 500 字符** → 对该段用 `\n`（换行）再切
3. **如果还 > 500** → 用 `。`、`！`、`？`（句子边界）切
4. **还是太长的极端情况** → 用 `；`、`，`（子句边界）切
5. **最后手段** → 在第 500 个字符处硬切

这种"递归下降"策略的精髓在于：**尽量在自然语义边界处切割，而不是简单地数字数。** 同样是 500 字符，切在句号后和切在句子中间，语义完整性有天壤之别。

## 第三层：向量化——给文本"打指纹"

### 先讲结论

```javascript
const embeddings = new OpenAIEmbeddings({
  model: 'text-embedding-v3',
  dimensions: 1024,                // 输出 1024 维向量
});

const vector = await embeddings.embedQuery("段誉在无量山学会了凌波微步");
// → [0.023, -0.145, 0.887, ...]  ← 1024 个浮点数
```

**向量化（Embedding）是让机器"理解"文本语义的魔法。** 它把一段文字变成一个长度固定（1024 维）的浮点数数组。在这个 1024 维空间中，语义相近的文字距离近，语义无关的文字距离远。

### 向量到底是什么？——一个视觉化的理解

不要被"1024 维"吓到。虽然人类无法直观想象 1024 维空间，但原理可以从 2 维推导：

想象你有一个"文本点阵图"，只考虑两个维度——**武侠**和**爱情**：

```
        爱情 ↑
             │
     王语嫣 · │         · 神仙姐姐
             │
     ────────┼──────────→ 武侠
             │
     包不同 · │   · 扫地僧
             │         · 乔峰
             │
```

在这个简化的 2 维空间中：
- "王语嫣"的坐标是 (低武侠, 高爱情)
- "乔峰"的坐标是 (高武侠, 低爱情)
- "神仙姐姐"接近王语嫣（同属爱情线）
- "扫地僧"接近乔峰（同属武学线）

**现在把 2 维扩展到 1024 维。** 多出来的 1022 个维度不是"武侠"或"爱情"这样人类能命名的维度，而是 Embedding 模型在海量训练中自动发现的"隐式语义特征"——可能是"语气正式程度""叙事视角""时间线位置""人物关系密度"等等机器自创的维度名。

**关键直觉：** 你不需要理解每个维度的含义，你只需要相信——"意思相近的文本，向量也相近"。这就是 Embedding 模型被训练出来要做的事。

### 为什么是 1024 维？

text-embedding-v3 支持多种输出维度：256、512、1024。这里选 1024 的原因：

| 维度 | 向量文件大小 | 语义精度 | 检索速度 | 选它的场景 |
|------|-------------|----------|----------|-----------|
| 256  | 小           | 粗       | 极快     | 手机端本地检索 |
| 512  | 中           | 中       | 快       | 大规模数据/成本敏感 |
| **1024** | **大**   | **细**   | **较快** | **精度优先场景（本项目的选择）** |

**比喻：** 维度就像素描中的线条数量——用 256 条线能画出一张脸的大致轮廓，用 1024 条线能画出脸上的微表情。对于小说这种细节丰富的文本，值得多用一些"线条"。

### 一个你可能没想过的问题：向量到底存了什么？

很多人以为向量里存了"关键词"。不是的。一个 1024 维向量中的每个维度，都不是对应某个具体的词。它是一种"分布式表示"——意义分布在整个向量的所有维度上，而非集中在某个维。

更准确的理解是：**向量是在 1024 维空间中给这段文字找到了一个"位置"**。就像 GPS 用（经度, 纬度, 海拔）三个数字定位一个物理位置，Embedding 用 1024 个数字定位一个"语义位置"。两个语义位置的"方向接近程度"，就是它们的相似度。

## 第四层：向量数据库——建"语义索引库"

### 先讲结论

```javascript
const client = new MilvusClient({
  address: 'https://xxx.serverless.ali-cn-hangzhou.cloud.zilliz.com.cn',
  token: 'xxx'
});

await client.insert({
  collection_name: 'ebook4',
  data: [{
    id: '1_3_15',
    chapter_num: 3,
    content: '段誉学会了凌波微步...',
    vector: [0.023, -0.145, ...]  // 1024维
  }]
});
```

**Milvus 存的不是普通的"表格数据"，而是"向量 + 原文"的二元组。** 每条记录除了包含原文内容和元信息（章节号等），最核心的是一个 1024 维的向量——它是这段文字的"语义指纹"。搜索时，Milvus 不是比对文字，而是比对向量。

### 为什么必须用向量数据库？

你可能会问：普通数据库（MySQL、PostgreSQL）不能做这事吗？

**答案是：能做，但做不好。**

如果你在 MySQL 里存了 5000 条小说片段，想找到跟"段誉的武功"最相关的 5 条，你怎么办？

- **方法 A**：用 LIKE '%段誉%武功%' 做全文搜索 → 只能找到"字面匹配"，找不到"段誉学会了凌波微步"（因为没出现"武功"二字）
- **方法 B**：先用 Embedding 生成查询向量，再在应用层对 5000 条记录逐条计算余弦相似度 → 5000 次浮点运算，每次新问题都要重走一遍
- **方法 C**：用 Milvus → 建好索引后，毫秒级返回 Top-K

**方法 A 和方法 B 的局限本质上是一个问题：传统数据库的索引结构（B-Tree、倒排索引）是为"精确值"设计的，不是为"近似向量"设计的。** 就像你不可能用电话本（按姓名首字母排序）来找到"声音最像的人"——数据结构和查询目标根本不匹配。

### 集合（Collection）的设计——为什么不只存向量？

看一下这个 Collection 的字段设计：

```
┌──────────────┬──────────────┬────────────────────────────────────┐
│   字段名      │   类型        │  为什么要这个字段                    │
├──────────────┼──────────────┼────────────────────────────────────┤
│ id           │ VarChar(100) │ 主键：唯一标识，用于去重和更新         │
│ book_id      │ VarChar(100) │ 未来如果你导入《射雕》《笑傲》，       │
│              │              │ 可以用它区分不同书                    │
│ book_name    │ VarChar(200) │ 在检索结果中显示"出自《天龙八部》"     │
│ chapter_num  │ Int32        │ 用户问"在哪一章？"时你要能回答         │
│ index        │ Int32        │ 章内片段序号，定位到章内位置           │
│ content      │ VarChar(1w)  │ 原文！给 LLM 看的上下文就靠它          │
│ vector       │ FloatVector  │ 1024维语义指纹，做相似度搜索的核心     │
└──────────────┴──────────────┴────────────────────────────────────┘
```

**关键洞察：vector 做搜索，content 做回答。** 向量是用来"找"的（找到最相关的几条记录），内容是给 LLM"看"的（作为生成答案的上下文）。向量本身对人类毫无意义——你不能把 1024 个浮点数展示给用户看说"这就是答案"。

### 索引选择——IVF_FLAT 的原理

```javascript
await client.createIndex({
  index_type: IndexType.IVF_FLAT,
  metric_type: MetricType.COSINE,
  params: { nlist: 1024 }
});
```

**IVF_FLAT 的全称是 Inverted File with Flat encoding。** 拆开理解：

- **IVF（倒排文件）**：先用 K-Means 聚类算法，把向量空间分成 `nlist` 个"簇"（cluster），每个簇有一个中心点。搜索时先找最接近的簇，再在簇内搜索，而不是跟所有向量逐一比较。
- **FLAT（扁平编码）**：在簇内的搜索是"暴力"的——逐一比较，不做任何压缩或近似。这意味着簇内搜索是 100% 精确的。
- **nlist=1024**：聚成 1024 个簇。这个数字的选择跟数据量有关——数据量越大，nlist 应该越大。经验值：`nlist ≈ 4 × sqrt(N)`，其中 N 是总记录数。

**比喻：** 假设你在全国找最近的加油站。不做索引=开车去每个加油站实地测距（全量扫描）。IVF=先把全国分成 1024 个区（簇），然后你只需要在自己所在的区及相邻几个区里比较。虽然可能错过刚好跨在区边界上的最优解，但在 99% 的情况下，够用且极快。

### 相似度度量——为什么用 COSINE 而不是欧氏距离？

Milvus 支持两种主流度量方式：欧氏距离（L2）和余弦相似度（COSINE）。

**通俗理解两者的区别：**

- **欧氏距离（L2）**：衡量两个点之间的"直线距离"。在文本向量中，它会受文本长度影响——长文章的向量"长度"（模）通常比短文章大。
- **余弦相似度（COSINE）**：衡量两个向量"指向的方向"的接近程度，与向量的"长度"无关。

**为什么这里选 COSINE？** 在文本语义场景中，我们关心的是"说的是不是同一个话题"，而不是"说了多少字"。两段关于"段誉学六脉神剑"的描述，一段 200 字一段 500 字——用 COSINE，它们的向量方向接近，被评为相似；用 L2，它们的距离可能因为长度差异而被拉大。

**比喻：** 两个人站在操场上——COSINE 看的是他们"面朝哪个方向"，L2 看的是他们"站的位置离多远"。两个人可以站在两角但面朝同一方向（COSINE=高相似），也可以站在一起但朝向相反（L2=距离近但语义无关）。

# 下篇：查询管道（rag.mjs）

## 先讲结论：查询管道到底干了什么？

**从外面看：** 你在终端里输入问题，AI 给出基于小说原文的回答。

**从里面看，一个 RAG 查询走三步：**

```
用户问题："段誉会什么武功？"
    │
    ▼  [① 向量化问题]  问题 → Embedding API → 1024维向量
    │
    ▼  [② 向量检索]    在Milvus中搜索最相似的5个chunk
    │                   → "段誉学会了凌波微步..."(相似度0.92)
    │                   → "段誉又练成了北冥神功..."(相似度0.88)
    │                   → "六脉神剑乃是段家绝学..."(相似度0.85)
    │                   → ...
    │
    ▼  [③ 构建Prompt]  把检索到的5段原文+用户问题拼成完整提示词
    │
    ▼  [④ LLM生成]     通义千问阅读5段原文 → 组织语言 → 生成答案
    │
    ▼
"段誉会的武功包括：凌波微步（轻功身法）、
北冥神功（内功心法，可吸人内力）、
六脉神剑（段氏绝学，以指力发出剑气）..."
```

**与 ChatGPT 的本质区别：** ChatGPT 的回答基于"训练时记住的东西"——它可能记错了，可能记混了，可能编造了。而 RAG 的回答基于"刚刚检索到的原文"——每一步都有据可查。你能展开"检索来源"看到原文是什么。

---

## 第一步：问题向量化——让机器"听懂"你的问题

```javascript
const queryVector = await getEmbedding("段誉会什么武功？");
```

这一步跟摄入管道中给 chunk 做向量化用的是**同一个模型**（text-embedding-v3）、**同一套参数**（dimensions=1024）。这个"同一性"极其关键。

**为什么必须用同一个模型？** 因为不同 Embedding 模型的"语义空间坐标系"是不同的。用 A 模型给书建向量，用 B 模型给问题做向量——就像一个人用墨卡托投影画地图，另一个人用高斯投影找路，坐标系统不兼容，找到的位置可能差十万八千里。

**比喻：** 你埋了一个宝藏，用 GPS（WGS-84 坐标系）记录了坐标。十年后你回来找，如果用北斗坐标系去解读那个坐标数字——挖到的可能是一片荒地。Embeddings 就是这里的"坐标系"。摄入和查询必须用同一套坐标系。

---

## 第二步：向量检索——在"语义空间"中搜书

```javascript
const searchResult = await client.search({
  collection_name: 'ebook4',
  vectors: [queryVector],
  limit: 5,                        // 返回 top-5
  metric_type: MetricType.COSINE,  // 余弦相似度
  output_fields: ['id', 'content', 'book_id', 'chapter_num'],
});
```

**这一步是整个 RAG 系统的"核心杠杆"——它把"关键词匹配"变成了"语义匹配"。**

假设用户问的是"段誉会什么武功"，在 MySQL 里用 LIKE 查：
- ✅ "段誉在无量山修炼武功..." → 匹配（包含"段誉"和"武功"）
- ❌ "那公子学会了一套精妙的步法，进退趋避，潇洒自如" → 不匹配（虽然说的就是凌波微步，但没出现"段誉"和"武功"）

在 Milvus 里用向量查：
- ✅ "段誉在无量山修炼武功..." → 相似度 0.95
- ✅ "那公子学会了一套精妙的步法..." → 相似度 0.88（语义相近！）
- ❌ "今天天气很好，万里无云" → 相似度 0.12（无关内容被正确排除）

**这就是向量检索的威力——它检索的是"意思"，不是"字面"。**

### Top-K 的选择（为什么是 5？）

```javascript
const retrievedDiaries = await retrieveRelevantContent(question, k=3);
// 实际使用时改成了 k=5
```

k 太小的代价：相关信息没被检索到，LLM "无米之炊"，只能回答"不知道"。
k 太大的代价：混入不相关的噪声，LLM 被干扰，生成质量下降；且 Prompt 变长，费用增加。

**5 是一个经验上的平衡点。** 对小说这种叙事性文本，一个问题的相关信息通常分布在 2-5 个不同的段落中。比如问"乔峰的身世"，相关信息可能出在雁门关大战（揭示身世之谜）、少室山（父子相认）、聚贤庄（契丹人身份暴露）等多个章节。

---

## 第三步：构建 Prompt——"把凿子给雕刻家"

这是 RAG 中最"软"但最见功力的部分。很多人以为 RAG 的核心是向量检索，实际上 **Prompt 的设计质量直接决定了最终答案的质量**。

```javascript
const prompt = `
你是一个专业的《天龙八部》小说助手。
基于小说回答问题，用准确、详细的语言。请根据以下小说片段内容回答问题：

[片段1] 章节号:3, 内容:段誉在无量山剑湖宫底...学会了凌波微步...
----
[片段2] 章节号:5, 内容:段誉又发现北冥神功图谱...
----
[片段3] 章节号:42, 内容:段誉在少林寺使出六脉神剑...
----

用户问题：段誉会什么武功？

回答要求：
1. 如果片段中有相关信息，请结合小说内容给出详细准确的回答，如果没有请说不知道。
2. 可以综合多个片段的内容，提供完整的答案。
3. 如果片段中没有相关信息，请如实告知用户。
4. 回答要准确，符合小说情节和人物设定。
5. 可以引用原文内容来支持你的回答。

ai助手的回答：
`;
```

### Prompt 设计的五个关键决策

**① 角色设定（"你是专业的天龙八部小说助手"）**

这不是装饰。System Prompt 的角色设定会显著影响模型输出的风格和准确性。你说"你是助手"，它给出通用回答；你说"你是专业的小说助手"，它会更注重情节准确性和引用原文。这是一种"心理暗示"——模型在训练过程中见过无数类似的角色设定模式，它真的会调整输出风格。

**② 结构化上下文（`[片段N] 章节号:X, 内容:...`）**

为什么要加编号和章节号？因为你要让模型能"自证其说"——回答里可以写"根据第 3 章的内容，段誉在无量山..."，这给用户的信任感远强于没有出处的回答。同时也是为前端展示"检索来源"做准备。

**③ 指令的精确性（"如果没有，请说不知道"）**

这是反幻觉的关键指令。不加这句话，模型在面对不相关上下文时，可能从自己的训练数据中"脑补"答案——这就绕过了 RAG 的意义。加上"请说不知道"，模型会更诚实地承认知识的边界。

**④ 允许多片段综合（"可以综合多个片段的内容"）**

不加这句，模型可能只回答第一个片段的内容而忽略其他片段。对于开放式问题（"讲讲乔峰的故事"），相关信息分布在多个片段，需要综合理解才能给出完整答案。

**⑤ 要求引用原文**

这是"可验证性"的保证。用户看到回答后可以对照原文确认——如果 AI 说错了，用户能发现。这是 RAG 与黑盒模型最大的区别：**你可以验证答案的正确性。**

## 第四步：LLM 生成——"雕刻家用凿子雕刻大理石"

```javascript
const response = await model.invoke([new SystemMessage(prompt)]);
console.log(response.content);
```

**为什么在 RAG 中推荐 temperature=0.7？**

```javascript
const model = new ChatOpenAI({
  temperature: 0.7,  // 介于保守(0)和狂放(1.5)之间
});
```

在 RAG 场景中，temperature 的选择与纯对话不同：

| temperature | 行为 | RAG 中适用吗？ |
|-------------|------|---------------|
| 0           | 确定性强，每次相同输入输出完全相同 | 太死板，缺乏自然语言流畅性 |
| **0.7** | **输出自然流畅，有适度的表达多样性** | **✅ 小说的最佳选择** |
| 1.5         | 脑洞大开，可能跑偏 | 可能编造情节，风险高 |

因为 RAG 已经用检索结果"锚定"了回答范围（模型不能胡说，有原文约束），所以在表达上可以适当放松——允许模型用自己的话组织语言，让回答读起来自然而不是机械地复制粘贴原文。

**比喻：** 检索结果是"食材"（小说原文），temperature 是"火候"。火太小（0）→ 食材是生的，不好吃；火太大（1.5）→ 食材炒糊了，偏离本味；中火（0.7）→ 食材熟透，色香味俱全。

## 交互设计：持续对话循环

```javascript
while (true) {
  const question = await askQuestion();  // 等待用户输入
  if (!question || question === 'exit') break;

  const prompt = await answerEbookQuestion(question, 5);
  const response = await model.invoke([new SystemMessage(prompt)]);
  console.log(response.content);
}
```

**为什么是命令行交互（readline）而不是 Web 界面？**

注意：`rag.mjs` 使用终端交互，而 `server.mjs` 提供了 Web 界面。这是有意为之的"双模式设计"：

- **终端模式（rag.mjs）**：适合开发调试。你可以直接在终端里对话，观察每一步的检索结果和相似度分数，快速迭代 Prompt。不需要打开浏览器、不需要前端环境——最少的环境依赖意味着最快的开发循环。
- **Web 模式（server.mjs + index.html）**：适合产品演示。普通用户不会打开终端，他们需要的是一个漂亮的网页。

两者共享同一套 RAG 核心逻辑（Embedding → Milvus 检索 → Prompt 构建 → LLM 调用），只是交互层不同。这是"关注点分离"的良好实践。

# 专题：EPUB 电子书在 RAG 中的地位

## 为什么在电子书 RAG 中，EPUB 是优于 PDF 和 TXT 的选择？

用一张对比表说清楚：

| 特性 | TXT | PDF | EPUB |
|------|-----|-----|------|
| 章节结构 | 无/靠正则猜 | 提取困难 | ✅ 原生支持 |
| 文本提取难度 | 零（就是文本） | 高（需要 OCR 或解析） | ✅ 低（HTML 清洗即可） |
| 元信息（书名/作者） | 无 | 提取困难 | ✅ 内置 metadata |
| HTML 标签干扰 | 无 | 无 | 需清洗，但简单 |
| 插图/版权页识别 | 无法自动识别 | 困难 | ✅ 靠文件边界判断 |

**核心结论：EPUB 是 RAG 场景下的"最优电子书格式"，因为它天生带着结构——分章、分段、元数据——这些结构信息在 RAG 的加载阶段可以直接利用，而不需要后处理去"猜"。**

TXT 的问题不是不能做，而是你需要额外写大量正则表达式去识别章节边界，而且准确率永远达不到 100%。PDF 的问题更严重——文字提取本身就是一座大山（尤其对中文竖排、分栏、图文混排的场景）。

---

## EPubLoader 的内部原理深度剖析

LangChain 的 EPubLoader 在底层使用了 `epub2` 这个 npm 包（见 package.json）。它的工作流程可以细化为 6 步：

```
① 解压 ZIP
   epub → 临时目录，释放所有文件
         ↓
② 解析 container.xml
   找到 rootfile 路径（通常是 OEBPS/content.opf）
         ↓
③ 解析 content.opf
   提取：书名、作者、所有章节文件的路径列表（spine）
         ↓
④ 逐个读取 XHTML 文件
   按 spine 顺序读取每个章节的 XHTML 内容
         ↓
⑤ HTML → 纯文本
   剥离 <p>、<div>、<span>、<br> 等标签
   保留段落间的换行（对后续 splitter 很重要）
         ↓
⑥ 组装 Document 对象
   每个章节 → { pageContent: "纯文本", metadata: { source: "文件名", ... } }
```

**第六步中 `splitChapters: true` 的作用，就是决定在第⑥步返回一个 Document 还是多个 Document。**

## 本次实践中遇到的 EPUB 实际问题

**问题1：插图页干扰**

《天龙八部》EPUB 中有一些只有一两行文字的页面（插图页的图片说明），内容长度 < 100 字符。如果不处理，这些"空壳章节"会被正常分块、向量化、存入数据库。用户在检索时会匹配到一段"见图"之类毫无意义的内容。

**解决方案：** 在 `loadAndProcessEPubStreaming` 中加入 `if (chapterContent.length < 100) continue;` 过滤。这是一个简单的启发式规则，但非常有效。

**问题2：HTML 实体残留**

EPUB 的 XHTML 中有时包含 `&nbsp;`、`&mdash;` 等 HTML 实体。大多数情况下 EPubLoader 会处理它们，但如果遇到清洗不完全的情况，需要在应用层做一次 `replace(/&[a-z]+;/g, ...)`。本项目使用的 EPubLoader 版本（`@langchain/community` 最新版）处理得比较好，未遇到此问题。

**问题3：章节元数据不完整**

有些 EPUB 的 `content.opf` 中 spine 项没有明确的章节标题，导致 Document 的 metadata 中缺少章节名。本项目通过维护一个 `chapterIndex + 1` 作为章节号，而非依赖 EPUB 内部的章节标题——这样虽然丢了"第X章 青衫磊落险峰行"的文学标题，但保证了章节编号的稳定性。

## 三个关键数字

| 数字 | 含义 | 为什么是这个值 |
|------|------|---------------|
| **500** | chunk_size（字符） | 一段完整情节的长度，语义单元的自然边界 |
| **1024** | 向量维度 | text-embedding-v3 的高精度档位，精度与成本的甜点 |
| **5** | 检索片段数（Top-K） | 足够覆盖多章节信息，又不会引入太多噪声 |

## 一个核心思想

**RAG 的本质不是"让 AI 更聪明"，而是"给 AI 一本书，让它查了再回答"。**

就像你不会让律师凭记忆引用法条（那样会出错），你会让律师翻法典、找到具体条款、再给你意见。RAG 就是给 AI 的"法典检索系统"——AI 负责阅读理解和语言组织，向量数据库负责精确检索，原文负责提供事实依据。

三者分工明确、各司其职、互相制约。这就是 RAG 的美。
